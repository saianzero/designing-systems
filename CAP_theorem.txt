CAP Theorem


* Consistency: every read receives the most recent write or an error.
* Availability: every request receives a response that is not an error.
* Partition tolerance: the system continues to operate despite an arbitrary number of messages being dropped (or delayed) by the network between nodes

CAP theorem implies that in the presence of a network partition, one has to choose between consistency and availability

* CAP is frequently misunderstood as if one has to choose to abandon one of the three guarantees at all times. In fact, the choice is really between consistency and availability only when a network partition or failure happens; at all other times, no trade-off has to be made.

During a network partition, systems designed for strong consistency may sacrifice availability, while systems designed for high availability may return potentially stale/inconsistent data.



BASE is a design philosophy commonly used in distributed/NoSQL systems where availability and scalability are prioritized over immediate consistency.

BASE =
* Basically Available → the system generally responds, even during failures.
* Soft state → data may change over time even without new user input, because replicas are synchronizing.
* Eventually consistent → if no new updates occur, all replicas will eventually converge to the same value.

Example: In a distributed database, you update your profile name, but one replica may temporarily still return the old name; eventually all replicas see the new name.

Think: ACID → strong consistency; BASE → eventual consistency (as a rough mental model).
